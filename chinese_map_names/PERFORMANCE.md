# 名称队列性能核验

这是 Lua 5.2 模拟基准，不是实机帧率或整局载入时间测试。功能、命名结果、每批 64 条命令、重试间隔和依赖检查顺序保持不变。

## 瓶颈与修改

此前每个批次都从完整队列重建实体查找表，即使所有居民均无依赖也会遍历整表。队列中的空 `dependencies` 表和只用于初次排序的 `order` 字段还会随每次状态读写复制。

现在仅在准备或恢复队列时建立一次实际依赖源的数字索引，保存后可直接恢复；去掉空依赖表与排序后不再使用的字段。依赖原始实体 ID、队列数组顺序、完成标记、游标和重试信息保留。`prepareRevision` 仍为 8，当前版本的未完成队列不会因本次优化退役或重置。

等待依赖时对尚未完成项目的实体名称检查保持原顺序，这保证外部改名、删除和继承名称变更的识别时机不变。没有增加定时器、世界扫描或常驻任务。

## 可复现方法

在仓库根目录运行：

```sh
python chinese_map_names/tools/benchmark_queue.py --baseline 3bb40cc --sizes 2048 8192 --repeats 5
```

脚本从指定 Git 基线和当前工作树加载真实的 `events.script.lua`、`queue.lua`，通过 `lupa.lua52` 执行。输入是已经准备好的当前版本任务：独立居民，或 8 个城市、64 个依赖城市的工厂及其余居民。所有对象都有可写名称，改名命令在当前 update 返回后生效，下一次 update 读取确认。

计时包含完整队列处理和模拟 `state:get/set` 的深拷贝；不包含名称规划、资源加载和末尾世界审计。原生实体与命令 API 使用确定性桩。耗时、Lua 指令计数和 `ipairs(entries)` 元素访问计数分别运行，计数插桩不混入计时。每组比较命令顺序及提交 update 的校验值、命令数、组件查询数、update 次数及最终计数。

## 2026-10-09 本机结果

5 次计时中位数；绝对时间因设备、负载和原生状态实现而异。

| 队列 | 基线 | 优化后 | 耗时减少 | 基线/优化后 Lua 指令约数 |
| --- | ---: | ---: | ---: | ---: |
| 2,048 个独立居民 | 122.25 ms | 89.65 ms | 26.7% | 14,801,000 / 11,081,000 |
| 2,048 个城市、工厂及居民 | 127.29 ms | 90.86 ms | 28.6% | 14,936,000 / 11,298,000 |
| 8,192 个独立居民 | 2,010.24 ms | 1,419.12 ms | 29.4% | 222,649,000 / 164,339,000 |
| 8,192 个城市、工厂及居民 | 2,003.67 ms | 1,380.10 ms | 31.1% | 223,155,000 / 165,163,000 |

8,192 项混合队列的 `ipairs(entries)` 访问从 1,073,235 次降为 32,851 次。前后均为 8,192 条命令、24,640 次组件查询、130 次 update、260 次状态读写，全部成功；命令顺序及所在 update 校验值相同。这一计数用于衡量被移除的整表扫描，并不包含队列本身必要的数字下标访问。

## 原生依据与边界

- `game_mechanics.zip!game_mechanics/company/company.script.tl:392` 和 `towns/towns.script.tl:242` 使用 `initNewGameFromMap` 初始化预设地图任务。
- `mission.zip!mission/name_util.tl:65–76` 在写入前检查实体和 NAME，使用原生命令；本次保留现有写入与回读确认流程。
- 状态继续使用项目已采用的 `state:get/set` 生命周期，没有改用尚未核实实际用法的原生状态旁路。
- 游戏内名称生成依据见 [NATIVE_NAMING.md](NATIVE_NAMING.md)。基准没有宣称真实游戏帧率提高，原生状态序列化耗时仍须实机测量。
